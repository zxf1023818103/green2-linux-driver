# USB 换主机调查（2026-11-11）

结论：曾出现一次 WHC 初始化命令超时，但后续真实换主机及软件重枚举均能恢复，
不能把“换主机必须复位”当作已证实的限制。本轮没有修改或重刷固件/内核模块。

## 原始故障

Green2 从 Android 接到电脑并交给 Core 26 虚拟机后，USB 描述符已枚举，蓝牙
控制器可用。Wi-Fi probe 在约 9.114 秒开始，约 11.128 秒报告
`Host API 0x7 response timeout`，随后 `llhw init fail`。

0x7 是 `WHC_API_WIFI_SET_USR_CFG`：驱动初始化的首条 WHC 命令。此时尚未创建
可用 Wi-Fi 接口，也未进入 NAN/PASN 配对。COM41 RTS 复位模组后 probe 恢复。
这只能证明复位能够恢复当时状态，不能证明根因或必须使用 RTS。

原始失败窗口没有 USB URB 传输抓包或固件任务/端点状态快照，因此无法区分：
命令未完成 USB OUT、固件未处理命令、回复未完成 USB IN，或主机未接收/匹配回复。
不能仅根据 timeout 将责任确定归于 VMware、Linux、蓝牙或固件某一方。

## 后续验证

| 操作 | 结果 | RTS/MCU 复位 |
| --- | --- | --- |
| Wi-Fi 接口 unbind/bind | 3/3 通过 | 无 |
| USB device authorized=0/1 | 3/3 通过 | 无 |
| USBDEVFS_RESET 总线复位 | 3/3 通过 | 无 |
| VM 关机释放给 Windows，8 秒后重新交给 VM | 1/1 通过 | 无 |
| PC → YM6252，模组保持运行 | 初始化通过，重新发布两项 NAN 服务 | 无 |
| YM6252 → PC，Android NAN 发布中直接拔线 | 初始化通过，Core 26 自动恢复两项服务及 TCP 8000 | 无 |

最后一轮 Core probe 时间为 183.671546 秒，183.676359 秒已走到初始化后的
区域配置日志；新启动窗口没有 0x7 timeout。USB 总线复位不等于重启模组 MCU。
这些测试排除了固定必现的主机切换失败，但不能排除低概率竞态。

## 下一次故障需要保留什么

先不要立即 RTS 复位：记录 USB 设备/接口/端点、内核 probe 时间、URB 提交和
完成状态，以及 COM41 串口。核查 EP5/6/7 OUT 是否完成、EP4 IN 是否返回
相应 WHC API 消息，再决定检查固件工作队列/发送信号量还是主机接收路径。
原始串口、握手和抓包留在本地，避免公开配对材料。

本轮 USBmon 只取得了正常总线复位窗口；真实物理切换时的 USBmon 未就绪，
该次成功由内核初始化日志、接口状态和服务发布状态确认，不能把它当作失败
事务的 USB 抓包。后续抓包应在拔线前先确认 usbmon 已加载且采集进程存活。

## 独立的蓝牙应用现象

Core 26 在 USB 重插后仍有蓝牙控制器，但原 BLE Python 进程没有自动重新注册
广播，ActiveInstances 为 0。重启 `green2-nan-ble.ble` 服务恢复广播；不需要
重启模组。此现象属于 BLE 应用热插拔恢复，与首条 Wi-Fi WHC 命令超时分开记录。
